# 003 — Phase 3 市場セグメント + PPM 実UI

策定日: 2026-07-30 ｜ 対応ペルソナ: `docs/PERSONAS.md` ①佐藤（経営企画・フレームワークの実感）中心
背景: `config/theories.ts` に PPM（BCGマトリクス）は figure として入っているが、**単一市場モデルのため縦軸（市場成長率）が製品ごとに存在しない**。「どの事業に金を注ぎ、どれを見切るか」という PPM の問いをプレイヤーが実際に問われる場面がなく、理論が図鑑の中だけで閉じている。`game.marketShare` も会社単位の単一値で、多角化・撤退という打ち手そのものが存在しない。

## 設計判断（2026-07-30 ユーザー確定）

| 論点 | 決定 | 補足 |
|---|---|---|
| Phase 3 の着手順 | **市場セグメント + PPM 実UI から** | 最後に残った大きなゲーム性の追加。配信系（モバイル/シェア）はゲームが仕上がってから |
| 収益化方針 | **100円買い切り** | `plan.md` で保留されていた判断。本仕様の実装内容には影響しないが、Android 化（plan.md Phase 7）の設計前提として確定 |

## 設計判断（実装者判断・要確認事項は各項に明記）

| 論点 | 決定 | 理由 |
|---|---|---|
| セグメント数 | **4** | PPM の2×2に各象限が埋まりうる最小数。多いと週次テンポの中で管理しきれない |
| 成長率の扱い | **セグメントごとに時間変動**（新興は高成長→成熟で鈍化） | 固定値だと「最初に高成長を選ぶだけ」の一択ゲームになり、PPM の「入れ替え判断」が発生しない |
| 既存 `marketShare` | **据え置き（導出値にしない）** | 当初は「加重平均として導出」する設計だったが、実装時に marketShare を直接書き換える箇所が**9つ**（マーケ実行 / 決裁3箇所 / 訪問者 / 競合攻撃2箇所 / 週次イベント / 製品駆動）あることが判明。導出値にするとこれらの効果を毎月上書きして黙って消すため、方針を変更した。製品駆動のシェア成長だけをセグメント経由にし、その全体換算分を marketShare に加算する |
| 製品とセグメント | **製品は開発時に1セグメントを選ぶ（後から変更不可）** | 「どこに賭けるか」を意思決定にするため。撤退で畳むことはできる |

## スコープ

### A. 市場セグメント基盤（managers 層）
- `config/marketSegments.ts` に4セグメント（規模・成長率・成長カーブ・競合圧）
- `Product.segmentId` を追加。製品はいずれかのセグメントに属する
- `game.segmentShares` にセグメント別の自社シェアを保持する。`game.marketShare` は据え置き（上の設計判断を参照）で、製品駆動の成長分だけをセグメント経由で加算する
- 売上計算にセグメントの規模・成長率・自社シェアを反映する（Phase 1 の売上ドライバー分解にも新しい寄与として出す）

### B. PPM 実UI
- `classifyProduct()`: 縦軸＝所属セグメントの成長率、横軸＝**相対シェア**（自社セグメントシェア ÷ 最大競合のセグメントシェア）で花形／金のなる木／問題児／負け犬に分類
- 市場タブに2×2マトリクスを実データで描画し、各製品をプロット
- 象限ごとの定石（花形＝投資継続／金のなる木＝収穫／問題児＝集中か撤退／負け犬＝撤退）を1行で提示する

### C. 多角化・撤退の意思決定
- 製品開発時にセグメントを選ぶ UI（Wave 1 で先行実装済み — 製品にセグメントを持たせる時点で必須になったため）
- 撤退アクション（製品を畳む。売上を失う代わりに保守負荷＝ストレスが下がる）
- PPM 理論の解禁条件を「製品3本」から「2セグメント以上に展開」へ寄せる検討（**要確認**: 既存の解禁条件を変えると過去セーブの体験が変わるため、追加条件にとどめる案が有力）

## 実装順序（依存関係）

1. **Wave 1: A**（セグメント基盤。UI 変更は最小限）
2. **Wave 2: B**（PPM 分類 + マトリクス描画。A のデータが揃ってから）
3. **Wave 3: C**（セグメント選択と撤退。B で「見えた」あとに「動かせる」ようにする）

## 実装状況

### Wave 1（A: 市場セグメント基盤）— 実装済み（2026-07-30）

| 項目 | 実装 |
|---|---|
| セグメント定義 | `config/marketSegments.ts` に4セグメント（エンタープライズ／中小SaaS／コンシューマ／AI）。規模・初期成長率・成熟月数・成熟後成長率・競合の厚み |
| 成長率の時間変動 | `getCurrentGrowthRate()`。開始時の成長率から `maturityMonths` をかけて成熟後の値へ線形に鈍化。AI は9.0%→1.0%（15ヶ月）で、初期の優位が永続しない |
| 製品とセグメント | `Product.segmentId`。開発時に参入市場を選ぶモーダル（`ui/segmentSelection.ts`）。各選択肢に成長率・自社シェア・競合・規模を明示（週次イベントと同じ「数字を出す」方針） |
| セグメント別シェア | `game.segmentShares`。製品を持つセグメントだけが伸び、伸び幅は「製品数 × 現在成長率」 |
| 売上への反映 | `getSegmentSalesMultiplier()` を売上の乗算チェーンに追加。ドライバー分解にも `segment`（市場セグメント）として出る |
| 旧セーブ互換 | `normalizeGameState()` で `segmentShares` を全セグメント0初期化。`segmentId` 未設定の製品は既定セグメント（中小SaaS）扱い |

**検証**: tsc 0 / Vitest 306 緑（Wave 1 で +23）/ `scripts/e2e-wave1.mjs` 24 チェック全 PASS（セグメント選択の表示・選んだ市場のシェアだけが伸びること・ドライバーに `segment` が出ることを追加）。

**バランス再測定**（`scripts/balance-scenario.mjs`、15回・ノーマル）: **クリア率 27%**（Phase 2 完了時点は40%）。許容帯（10〜90%）内だが低下している。原因は素朴な自動プレイが常に AI セグメント（規模×1.1）を選ぶ一方、シェア成長が規模で重み付けされて全体シェアへの寄与が薄まるため。勝ち筋（製品3本＝クリア4件すべて）と負け筋（製品1本＝ゲームオーバー11件中9件）の差は Phase 2 と変わらず維持されている。調整ノブは `SegmentManager.BASE_SHARE_GAIN` と `config/scenarios.ts` の `startingMoney`。
