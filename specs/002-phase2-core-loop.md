# 002 — Phase 2 遊びの骨格

策定日: 2026-07-20 ｜ 対応ペルソナ: `docs/PERSONAS.md` ②田中（緊張感）③中村（短尺）中心
背景: 1クリック=1週・月次決算は第4週のみのため、4週中3週が無イベントの空振りでペルソナ共通核「打ち手→数字の因果の体感」が希釈されている。`employeeResignChance`（gameConfig.ts 定義済み）は未使用、`burnout_prone`/`inconsistent` 特性も効果がなく、打ち手を誤るリスク＝緊張感が存在しない。現状はクリア条件のないサンドボックスで起承転結がない。

## 設計判断（2026-07-20 ユーザー確定）

| 論点 | 決定 | 補足 |
|---|---|---|
| テンポモデル | **B: 週次ミニイベント充填** | 週構造は維持し、空白週にコンテンツを充填する |
| 初回シナリオ | **起業1年目** | 12ヶ月生存。既存の資金繰り・破産機構で成立し追加機構が最小 |
| CEO前面化 | **決裁カードを管理モードに注入** | 決裁カードが週次イベントの主力になり、B案の懸念（コンテンツ量産）を既存 CEO モード資産の転用で緩和する |

## スコープ

### A. 週次ミニイベント基盤
- 決算週以外の各週で、イベントプールから抽選して1件提示する（週あたり最大1件 — 水増しノイズ化の防止）
- イベント種別: ①決裁カード（C）②人事イベント（B の予兆・面談）③市場・ニュース選択イベント（既存ニュースの選択肢付き拡張）
- **設計制約（共通核）**: 全イベントは選択結果の「数字への影響」を明示する（impact 表示は Phase 1 の a2ui 資産を流用）

### B. 退職・モチベーションの実効化
- motivation の変動源を整理（過重労働・放置・研修・決裁結果）し、`employeeResignChance` をモチベーション連動で接続
- `burnout_prone` / `inconsistent` 特性を実効化
- 予兆の可視化: アドバイザーカード（危険水域警告）+ キャラ stressed 状態（いずれも Phase 1 資産の転用）
- 退職は数字で見える損失にする（再採用コスト・開発力低下 → 売上ドライバーに反映）

### C. CEO決裁カードの管理モード注入
- DocumentManager 資産を管理モードの週次イベント（A のプール）として注入
- 決裁結果の理論タグ表示 + 図鑑解禁（v2.3.0 資産）を管理モードでも発火させる
- 訪問者システム等の CEO 専用機能は CEO モード据え置き（モード自体は統合しない）

### D. シナリオ「起業1年目」
- 新シナリオモード: 初期資金を絞った12ヶ月生存。資金ショート＝ゲームオーバー、12ヶ月生存＝クリア
- クリア/ゲームオーバー画面 + 事後講評の最小版（主要指標サマリ + 体験した理論の一覧。バックログ「経営を理論で振り返る」の v1）
- 既存の破産判定・難易度機構を流用

### E. 固定費（トレードオフの最小実装）
- オフィス維持費を月次固定費として P/L に計上（officeLevel 連動）
- D の資金繰り緊張感の燃料であり、Phase 1 の財務3表可視化と直結する

## 実装順序（依存関係）

1. **Wave 1: B + E**（managers 層のみ、UI 変更最小 — 緊張感の核）
2. **Wave 2: A + C**（週次イベント基盤 + 決裁注入。B の人事イベントをプールに接続）
3. **Wave 3: D**（シナリオ + クリア/講評画面。A-C が揃ってから12ヶ月の体験曲線を調整）

## 非スコープ

- 市場セグメント + PPM 実UI（Phase 3、テンポと統合設計必須のため）
- シナリオ「部門P/L再建」「上場」（起業1年目の実装パターン確立後に横展開）
- モバイル対応・収益化（Phase 3）

## 検証

- Wave ごとに Vitest（新規ロジックはテスト先書き）+ tsc 0 を維持
- UI 変更は実ブラウザ E2E 必須: `scripts/e2e-wave1.mjs` を Phase 2 チェック（週次イベント発火 / 退職発生 / シナリオクリア）へ拡張
- バランス検証: 起業1年目を実プレイ相当の自動進行で N 回走らせ、クリア率が極端（<10% / >90%）でないことを確認

## 実装状況

### Wave 1（B + E）— 実装済み（2026-07-30）

| 項目 | 実装 |
|---|---|
| B. モチベーション変動源 | `managers/RetentionManager.ts` `calculateMotivationDelta()`。過重労働（stress 連動）/ 休息 / 放置（`lastTrainingTurn` 起点）/ 研修（`HRManager.executeTraining` で加算）。決裁結果は `DocumentManager.processVerdict` が従来どおり直接反映（二重適用を避けるため RetentionManager では扱わない） |
| B. `employeeResignChance` 接続 | `calculateResignChance()`。モチベーション帯別の倍率で増幅し `maxResignChance` でクランプ。安全圏（70以上）は 0 |
| B. `burnout_prone` 実効化 | 判明済み＋高ストレスでモチベーション追加低下、退職確率も上乗せ |
| B. `inconsistent` 実効化 | 判明済みのみ月次で `performanceMultiplier`（0.2〜1.2）を振り直し、売上ドライバーの労働力寄与に反映 |
| B. 予兆の可視化 | 退職ゼロの月に限り a2ui アドバイザーカード（`buildRetentionAdvisorMessage`）。stressed アニメは既存 `updateMonthlyStress` のまま |
| B. 数字で見える損失 | 退職時に再採用コスト（月給×2）を当月 P/L へ計上 + 人員減が労働力ドライバー経由で売上に反映 |
| E. オフィス維持費 | `config/offices.ts` の `monthlyMaintenance`（L1 10万 〜 L5 350万）を `FinanceManager.getMonthlyFixedCost()` 経由で月次 P/L に計上 |

**設計上の決定**

- 売上ドライバーに `workforce`（社員のモチベーション）を追加した。基準モチベーション（`retention.neutralMotivation` = 70）ちょうどで係数 1.0 になるため、既存バランスの基準点は動かない。
- オフィス維持費に難易度 `costMultiplier` は掛けない（人件費と同じ扱い）。難易度は売上側で調整済みで、重ねると規模拡大コストだけが二重に効く。
- 退職は 1ヶ月最大1名・在籍1名は必ず維持（合法手が消えるのを防ぐ）。
- 旧セーブ互換は `gameStore.normalizeGameState()` に集約（`stress` / `lastTrainingTurn` / `performanceMultiplier` と、財務スナップショットの `fixedCost` / `attritionCost` を既定値で補完）。

**検証**: tsc 0 / Vitest 237 緑（Wave 1 で +45）/ `scripts/e2e-wave1.mjs` 13 チェック全 PASS（固定費の P/L 計上・労働力ドライバー・退職発生を追加。退職は確率判定のため決算ターンのみ `Math.random` を固定して決定的にしている）。

### Wave 2（A + C）— 実装済み（2026-07-30）

| 項目 | 実装 |
|---|---|
| A. 週次イベント基盤 | `managers/WeeklyEventManager.ts`。決算週（第4週）以外の各週で1件だけ抽選し `game.currentWeeklyEvent` に保持（週最大1件＝ノイズ化防止）。社長モードは対象外（決裁はデスクの本編なので二重提示しない） |
| A. イベント種別 | ①決裁カード（C）②人事イベント ③市場・ニュース選択イベント。②③は `config/weeklyEvents.ts` のデータ駆動。抽選は decision 0.5 / hr 0.25 / market 0.25 で、対象不在の種別は候補から外れ重みが再配分される |
| A. 数字への影響の明示 | `buildImpactLabel()` が選択肢の effect から表示文字列を生成し、適用（`applyEffect`）と同じ定義を読む。**表示だけ嘘になることがない** |
| C. 決裁カード注入 | `DocumentManager.generateDocuments(state, 1)` の書類を週次イベントとして提示。管理モードでは承認／却下のみ（差し戻し・調査・保留は CEO モード専用機能として据え置き） |
| C. 理論タグ + 図鑑解禁 | `processVerdict` が既に行うため管理モードでも自動的に発火。結果モーダルで既存 `verdict-theory-*` スタイルを再利用 |
| 放置の扱い | 未対応のまま次週へ流れたら失効（`expireWeeklyEvent`）。決裁カードならキューから外し提出者のモチベーション -3（放置＝意思決定の放棄） |

**設計上の決定**

- `processVerdict` を `state.ceo` null 安全化した。管理モードには CEO ステータスが無く、支持率・罠検知などの CEO 専用カウンタは単に加算されない（偽の CEO 状態を注入するより、加算しない方が状態の意味が正しい）。
- **モーダルの上書き対策**: 週次イベントのモーダルは実績解除など他の通知に上書きされうる（モバイル実機相当で再現）。`game.currentWeeklyEvent` が残る限り概要タブにバナー（`#weeklyEventBanner`）を出し、そこから開き直せるようにした。タイミング調整だけに頼らないための構造的な担保。

**検証**: tsc 0 / Vitest 264 緑（Wave 2 で +27）/ `scripts/e2e-wave1.mjs` 17 チェック全 PASS。E2E に「週次イベント提示（全選択肢に影響表示あり）」「バナーからの復帰」「決裁の解決と理論解禁」「決算週には出ない」を追加。モバイル相当（390×844）で両選択肢が折り返しの外に出ないことも実測。

### Wave 3（D: シナリオ「起業1年目」）— 実装済み（2026-07-30）

| 項目 | 実装 |
|---|---|
| シナリオ定義 | `config/scenarios.ts`。開始資金600万・12ヶ月生存。難易度の `startingMoney` を上書きする |
| 選択導線 | モード選択画面に3枚目のカード（🌱 起業1年目）。管理モードの操作系のまま勝利条件だけ載せる |
| 決着判定 | `managers/ScenarioManager.ts` `checkScenarioOutcome()`。破産をクリアより先に見る（最終月に落ちたら負け）。決着済みは再判定しない |
| 破産機構 | 既存の `FinanceManager` / `game.isBankrupt` をそのまま流用（新規の破産ロジックは足していない） |
| 進行の可視化 | 概要タブに「残り Nヶ月」を常時表示（期限があることを忘れさせない） |
| 事後講評 | `buildDebrief()` が主要指標7項目 + このプレイで体験した経営理論の一覧 + 数字から導いた講評文を返す（バックログ「経営を理論で振り返る」の v1） |

**設計上の決定**

- **決着画面の優先度**: 実績解除モーダル（`i*1000ms`）が結果画面を上書きする問題を実機で確認。結果表示を実績の後ろにずらしたうえで、`game.scenarioResult` が残る限り概要タブのバナーから開き直せるようにした（Wave 2 の週次イベントと同じ方針＝タイミングだけに頼らない）。
- 決着した月は週次ミニイベントを出さない（結果画面を邪魔しない）。

**検証**: tsc 0 / Vitest 283 緑（Wave 3 で +19）/ `scripts/e2e-wave1.mjs` 21 チェック全 PASS。

E2E は DOM 存在だけでなく **実際に可視か**（`getBoundingClientRect().height > 0 && offsetParent`）を見る。当初は存在チェックのみで、結果画面が非表示のまま PASS しかけた（偽グリーン）。

**バランス測定**: `scripts/balance-scenario.mjs`（CI には載せない手動実行）。実ブラウザで「2名確保 → 製品を最大3本 → 週次イベントは常に最初の選択肢」という素朴な方針で自動プレイし、クリア率を測る。

2026-07-30 の実測（15回・ノーマル難易度）: **クリア6 / ゲームオーバー9 = クリア率 40%** → 極端（<10% / >90%）ではないことを確認。負け筋は「製品1本のまま固定費に押し潰される」（ゲームオーバー9件中7件が製品1本）で、勝ち筋の「製品を3本まで伸ばす」との差が結果に出ている＝打ち手が効いている。この方針は最適プレイではないため、実際の上手いプレイのクリア率はこれより高い。開始資金は `config/scenarios.ts` の `startingMoney` 一箇所で調整できる。
