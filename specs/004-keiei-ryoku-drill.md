# 004 — 経営力ドリル（経営力のゲーミフィケーション）

**起点**: 2026-08-01、計算科目の試験でうまくいかなかった実体験。

敗因の自己分析は「スマホアプリやAIに頼ったインプットしかしておらず、実際の難易度と計算問題に
直面したとき、**どこでどの引き出しを開ければいいか分からなかった**」。
知識の不足ではなく、**知識を状況に接続する訓練の不足**が問題だった。

> 本リポジトリは public のため、個別の得点等は記載しない（判断の背景は非公開のメモリ側に置く）。

この痛みを、既存のビジネスシミュレーションゲームと組み合わせてプロダクト化する。

---

## コンセプト

> **経営力のゲーミフィケーション。**
> ゲームは「引き出しを使う場」、ドリルは「引き出しを研ぐ場」。データだけが両者を行き来する。

### ターゲット（2026-08-01 ユーザー確定）

**経営力向上を目指す日本のビジネスパーソン全般。その中に中小企業診断士受験生を含む。**

受験生セグメントが小さいこと（1次受験者は年間2万人規模）は認識した上での判断。
「刺さる人には刺さる」ことと、ゲーム性による学習という競争優位を重視する。

この決定から導かれる**設計上の制約**:

- 問題文の主語は常に**「あなたの会社」**。試験の設問番号・年度を出さない
- 「引き出し」は試験の分類ではなく**経営判断の型**として記述する
- 結果として、受験生には試験対策になり、それ以外の人には経営の訓練になる

### 収益モデル（要検討）

- **買い切り型**を念頭に置く（サブスクリプションではない）
- 価格は別途検討。100円は初期案であり確定ではない

### 対応デバイス

パソコン・スマートフォンを問わずプレイできること。
既存資産（Vite + Lit + Service Worker の PWA）がそのまま使えるため、Web を第一級とする。
Phase 7 の Capacitor による Android 化はこの上に乗る。

---

## 設計判断

### D-1. ゲームとドリルを1つの画面に混ぜない

**「ゲームの途中でクイズが出る」形式は採らない。** ゲームのテンポが切れ、ドリルは反復の規律を失う。
エデュテインメントが失敗する典型パターンであるため、構造的に回避する。

| | 役割 | ループの長さ |
|---|---|---|
| ゲーム | 引き出しを**使う**。判断を誤れば会社が傾く。問題は出ず、結果だけが返る | 長い（数十ターン） |
| ドリル | 引き出しを**研ぐ**。ゲームの決算データを題材に、判定と計算を訓練する | 短い（1問1〜2分） |

両者を繋ぐのは**データのみ**。

### D-2. 罠（誤答）は人が書かず、エンジンの中間計算値から導出する

本構想の中核。デモ版（Claude Artifact）は罠を手書きで列挙しており、
100問作るのに300個の中間値を人力で書くことになり、**コンテンツ生産がボトルネックになって死ぬ**。

シミュレーションエンジンはすでに答えを持っている。
`FinanceManager.calculateMonthlyRevenue()` の

```
profit = revenue - salaryTotal - interest - fixedCost - attritionCost
```

という減算チェーンを**途中で止めた値**が、そのまま「人が実際に落ちる場所」になる。
これはコードから機械的に取り出せるため、問題数はプレイした月数だけ増える。

### D-3. 2段階構造（引き出し判定 → 自力で数値入力）

デモ版の発明をそのまま継承する。

- **STEP 1**: この状況でどの引き出しを開けるか（4択）
- **STEP 2**: 選択肢なしで数値を入力し、完走する

成績は**判定率と完走率を別々に記録**する。「棚を間違えた」のか「計算で落ちた」のかで処方が違うため。

### D-4. 罠の除外基準は採点の許容誤差と揃える

2026-08-01 の垂直スライスで実データにより発覚した設計上の欠陥。詳細は「実装で得た知見」を参照。

## 引き出し（解法パターン）

`src/lib/config/drawers.ts` に定義。8種。

| key | 名前 | 開ける条件 |
|---|---|---|
| `difference` | 差額・増分で考える | 2案を比べるとき。どちらでも同じ金額（埋没原価）は両方から消す |
| `afterTax` | 税引後に直す | 税率が与えられたとき。費用削減は利益増＝課税対象 |
| `controllable` | 管理可能か不能か | 人や部門を評価するとき。その人が動かせる数字だけで測る |
| `denominator` | 分母・掛け先の対応 | 比率を出すとき。何と何を対応させる概念かを先に言葉で確認する |
| `accrual` | 支払⇔発生の変換 | 現金の動きと費用の発生がずれるとき |
| `discount` | 割引の完走 | 複数期にまたがるとき。現在価値に直すまでが1セット |
| `formula` | 公式に数値代入 | 一般論で答えたくなるとき。式を書いてから数字を入れる |
| `classification` | 貸借属性の識別 | 勘定科目が出たとき。名前の印象ではなく貸借の位置と機能で判定する |

## スコープ

### A. 生成エンジン（managers 層）— Wave 1 実装済み

- `DrillManager.generateProblemsFromSnapshot(snapshot)` — 1決算から問題一式
- `DrillManager.generateDrill(game)` — 最新決算からドリルを作る。決算が無ければ空
- `DrillManager.judgeAnswer(problem, input)` — `correct` / `trap` / `wrong` の3値判定

### B. ドリル UI — 未着手

- 2段階（引き出し4択 → 数値入力）の画面
- 罠を踏んだときに「どこで止まったか」を返す
- 引き出し別の判定率／完走率
- スマホ前提のレイアウト（既存の PWA に同居）

### C. 問題型の拡充 — 未着手

現在3型のみ。優先度順:

1. **NPV / 割引の完走** — オフィス投資判断と直結。診断士2次 事例IV の本丸
2. **差額原価収益分析** — 増床 vs 現状維持など、ゲーム内の実際の選択肢から生成
3. **税引後キャッシュフロー** — ゲームに税の概念がないため、仮定を置く形で層を重ねる

### D. ゲームとの接続 — 未着手

- ゲーム内で誤った判断（例: 損益分岐点を割る採用）を検知し、対応する引き出しを**優先出題**する
- ドリルの成績をゲーム側に還元するかは**要検討**（ゲームを勉強の人質にすると両方壊れる懸念）

---

## 非スコープ

- **2次試験の記述式**。自動採点できないため、別の仕組みが必要。今回は扱わない
- **過去問そのものの収録**。著作権上の懸念があり、かつ本構想の強みでもない。
  問題はすべてゲーム由来の数値から生成する
- **他資格への展開**。まず経営領域で成立させる

## 実装で得た知見

### 罠と正解が偶然接近する（実データで初めて出た）

垂直スライスを実際のゲーム進行に流した瞬間、**判定が反転するバグが2件**出た。

| 症状 | 実測値 |
|---|---|
| 罠「他人資本比率」が正解判定された | 正解 50.023% に対し罠 49.977%（差 0.046%） |
| 罠「実際の売上高」が正解判定された | 正解 2,840,000円 に対し罠 2,844,628円（差 4,628円） |

原因は、罠を除外する基準（完全一致）と採点の許容誤差（0.2%）が**別の物差しだった**こと。

**手書きの問題では永遠に起きない。** デモ版の 250,000 / 300,000 のようなきれいな数字は互いに
十分離れている。ゲーム由来の割り切れない数値だからこそ衝突した。

対処: `usableTraps()` を導入し、除外基準を採点と同一のヘルパー `withinTolerance()` に統一。
罠どうしの衝突も先勝ちで1つに寄せる（どちらの指摘が出るか不定になるため）。
上記2ケースは回帰テストに固定済み。

> **この構造は自動生成である限り再発する。** 新しい問題型を足すときは、必ず実際のゲーム進行に
> 流して `judgeAnswer` の判定を目で確かめること。フィクスチャの緑は根拠にならない。

## 事業性検証で判明したこと（2026-08-01）

### 看板は「誤答の自動生成」ではない

ビジネスゲーム（MG・TOPSIM・Cesim 等）が50年間 B2B 集合研修に留まり、個人向け非同期に
降りてこなかった主因は技術ではなく、**価値の大半がデブリーフィング（振り返り）に宿る**構造にある。
個人・非同期にするとこれが失われ、学習効果を主張できなくなる。

本プロダクトはこのピースを**すでに内蔵している**:

- `config/theories.ts` の設計原則「行動 → 後から理論で命名。先に講義しない」
- `ScenarioManager.buildDebrief()` の事後講評

したがって訴求は **「あなたのプレイを、経営理論の言葉で振り返らせる」**。
「誤答を自動生成できる」は実装の話であって顧客価値ではない。

### 変動費の不在（最優先の技術課題）

このゲームの費用は 給与・オフィス維持費・支払利息・再採用コスト・一時費用のみで、
**売上に連動する費用が存在しない**。帰結:

- 限界利益率が常に 100%
- 損益分岐点売上高が単なる固定費合計に退化（本来の `固定費 ÷ 限界利益率` にならない）
- CVP・差額原価・営業レバレッジが構造的に表現できない
- 8つの引き出しのうち実働は3つ

**「遊ぶことが経営の学習になる」を掲げる以上、これは看板に関わる欠陥。**
現状の `breakeven` 問題は「このゲームの中では正しいが、現実の経営では誤り」を教えうる。

対処は変動費率の導入（クラウド利用料・サポート費・決済手数料が自然な変動費）。
変動費率0から始めれば既存バランスと連続に移行でき、ゲームの判断の深さとドリルの正しさに
**同じ改修が同時に効く**。
